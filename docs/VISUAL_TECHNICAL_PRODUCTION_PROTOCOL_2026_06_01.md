# Visual Technical Production Protocol

Date: 2026-06-01

Purpose: define the technical contract for building premium SpaceBio-Bench
slides and manuscript visuals. This protocol is meant to prevent attractive but
fragile slides: every visual should be source-traceable, reproducible,
inspectable, editable where needed, and safe against overclaiming.

## Scope

This applies to:

- bridge/method slides B1-B8;
- layered result scenes Fig1/Fig2/Fig3/Fig6;
- v9 provenance/release-boundary slides;
- manuscript figure exports derived from the same evidence objects.

It does not replace scientific review. It defines the production layer that
makes the scientific review possible.

## Technical North Star

Every premium slide should be built as:

> source-verified evidence + reproducible scene plate + editable interpretation

That means:

1. the evidence object is traceable to a source file or manifest;
2. the scene plate is regenerated by a script;
3. the interpretation layer can be revised without changing the evidence;
4. the exported slide is visually inspected at full size and thumbnail size;
5. the visible caveat prevents the most likely overclaim.

## Visual Identity Gate

Do not treat the current light methods/provenance grammar as the brand.

Before producing more final-looking bridge slides, use:

- `docs/VISUAL_IDENTITY_RESEARCH_AND_DEPTH_STRATEGY_2026_06_01.md`
- `config/visual_identity/spacebio_bench_visual_identity_v0_1.json`

The selected direction is:

> Mission-grade scientific benchmark system

This is not NASA imitation. It is a disciplined hybrid of mission-system
seriousness, high-profile scientific editorial restraint, and premium
strategy-deck clarity.

Each new renderer should declare:

- slide type: `thesis`, `method_bridge`, `result`, `provenance`, or
  `manuscript`;
- visual identity token version;
- semantic color roles used;
- z-layers used;
- depth tokens used;
- anti-pattern checks, especially `no_card_box_layout`.

If a slide does not pass the visual identity gate, it can remain a logic
wireframe, but it should not be promoted as a premium deck candidate.

## Required File Contract

Each production slide should have a stable `slide_id`, for example:

- `b3_mission_held_out`
- `b4_train_only_guard`
- `fig1_tissue_transfer`
- `v9_public_bulk_boundary`

Recommended output layout:

```text
output/premium_bridge_scenes/<slide_id>/
  scene_plate.png
  rendered_preview.png
  rendered_preview.pdf
  overlay_spec.json
  manifest.json
  qa.json
```

For existing slide families that already use a flatter directory, keep the
current paths but preserve the same file roles.

### `scene_plate.png`

Contains:

- canvas/background;
- measurement layer;
- proof object or source-derived schematic;
- non-editable graphical texture only where needed.

Should not contain:

- long explanatory text;
- speaker-note content;
- internal file paths;
- reviewer instructions;
- visible planning language.

### `overlay_spec.json`

Contains:

- editable title text;
- editable callout text;
- focus rings;
- caveat/status label;
- normalized coordinates;
- font sizes;
- semantic colors;
- z-layer assignment.

This spec is the bridge to PowerPoint/Keynote/Google Slides/Canva. Even before
native slide export exists, the JSON should make the intended editable overlay
unambiguous.

Required fields:

```json
{
  "slide_id": "b3_mission_held_out",
  "canvas": {"width_px": 3840, "height_px": 2160, "aspect_ratio": "16:9"},
  "coordinate_system": "normalized_0_1",
  "text": [
    {
      "id": "headline",
      "role": "decision_headline",
      "content": "The test set is a mission, not a random sample",
      "x": 0.065,
      "y": 0.125,
      "font_pt": 26,
      "color": "ink",
      "max_lines": 2
    }
  ],
  "status_labels": [],
  "focus_marks": [],
  "forbidden_visible_terms": []
}
```

### `manifest.json`

Contains:

- slide ID and creation date;
- content brief path;
- evidence source path(s);
- source manifests or tables;
- claim boundary;
- visible terms;
- terms pushed to speaker notes;
- output files;
- generator script;
- deterministic seeds if applicable.

Required fields:

```json
{
  "slide_id": "b3_mission_held_out",
  "created": "2026-06-01",
  "content_brief": "docs/VISUAL_BRIDGE_CONTENT_BRIEFS_B1_B4_2026_06_01.md",
  "evidence_sources": [],
  "claim_boundary": "held-out mission evaluation; not random sample CV",
  "generator": "scripts/build_bridge_method_scenes.py",
  "outputs": {},
  "qa": {}
}
```

### `qa.json`

Contains machine-checkable and manual-review results:

- image dimensions;
- file existence;
- visible-word count;
- forbidden-term scan;
- contrast/readability result when available;
- thumbnail inspection status;
- full-screen inspection status;
- source-manifest presence;
- reviewer verdict.

## Canvas And Export Standards

### Slide Exports

Default:

- aspect ratio: 16:9;
- pixel size: `3840 x 2160`;
- matplotlib canvas: `figsize=(16, 9), dpi=240`;
- format: PNG and PDF;
- background included;
- deterministic random seed for texture/noise.

Acceptable secondary exports:

- `1920 x 1080` quick preview;
- `4032 x 2268` if matching a slide-tool export;
- contact sheet for family review.

Do not mix sizes within a family unless the manifest states why.

### Manuscript Exports

Default:

- PDF plus PNG;
- manuscript previews at target column width;
- color/grayscale QA if the figure carries quantitative meaning;
- no atmospheric layer unless it is part of a graphical abstract.

## Safe Area And Layout Grid

Use normalized coordinates.

Recommended safe area:

- left: `x >= 0.055`;
- right: `x <= 0.945`;
- top: `y <= 0.900`;
- bottom: `y >= 0.075`.

Primary headline zone:

- x: `0.060-0.520`;
- y: `0.090-0.230`;
- max 2 lines.

Evidence zone:

- bridge slides: central/right `0.200-0.900`, with large whitespace;
- result slides: right proof object `0.460-0.925`, unless slide-specific
  composition requires otherwise;
- provenance slides: document surface can occupy `0.170-0.890`.

Status/caveat zone:

- bottom-left or bottom-right;
- never directly under a busy data panel;
- should be readable but lower-emphasis than the headline.

## Typography Standards

For 3840 x 2160 slide exports:

| Text Role | Recommended Matplotlib Size | Notes |
|---|---:|---|
| Decision headline | 22-30 pt | short conclusion, max 2 lines |
| Section/chapter cue | 12-15 pt | optional |
| Primary callout | 10-13 pt | 2-6 words preferred |
| Secondary label | 7.5-9.5 pt | plain language |
| Status/caveat label | 7.0-8.5 pt | short and precise |
| Tiny source tag | 6.5-7.5 pt | only if not essential to live reading |

Minimums:

- no slide-critical text below 7.0 pt;
- no status/caveat below 6.5 pt;
- no line of visible text longer than roughly 48 characters unless it is a
  deliberate title.

Visible word-count targets:

- bridge/method slide: <= 45 words;
- result slide overlay: <= 30 words outside the proof object;
- provenance/release slide: <= 60 words if it replaces a table;
- appendix/table slide: explicit exception only.

## Text And Terminology Checks

Before rendering, classify terms into:

- visible;
- allowed only after first-use expansion;
- speaker-note only;
- forbidden visible text.

Default forbidden or discouraged visible terms:

- `LOMO` unless paired with `one mission held out`;
- `payload` unless paired with `data files`;
- `artifact rescue`;
- `RRRM scaffold`;
- `NES`;
- `macro-F1` unless the slide is about metrics;
- `alpha` unless paired with `metadata-only`;
- raw local paths;
- internal decision/review notes.

Preferred visible replacements:

| Internal Term | Reader-Facing Term |
|---|---|
| LOMO | held-out mission |
| payload | local data files |
| provenance | evidence trail or source trail |
| task manifest | task record, then task manifest in note |
| FM | foundation model |
| diagnostic-only | biology check or diagnostic lane |
| source inventory | source table or source record |

## Color And Contrast Standards

Use semantic color, not decoration.

Stable color roles:

- hidden/test mission: restrained red;
- training missions: green or neutral;
- gene-level input: blue;
- pathway summary: teal/green;
- model family / foundation model: violet, sparingly;
- status ready: green;
- status pending/blocker: muted red;
- diagnostic/caution: amber.

Contrast rules:

- decision headline must be high contrast against canvas;
- status labels may be lower emphasis but must remain readable in grayscale;
- red/green distinctions must also use position, shape, or labels;
- no meaning should depend on color alone.

## Layer Contract

Use the Z-stack deliberately:

| Layer | Technical Handling | QA Question |
|---|---|---|
| Z0 canvas | script-generated texture or flat field | Does it stay quiet? |
| Z1 measurement | thin rules, assay lanes, mission arcs | Does it explain the frame? |
| Z2 evidence | source-derived proof object or schematic | Is it traceable and readable? |
| Z3 interpretation | editable overlay text/callouts | Can wording change without rerendering proof? |
| Z4 trust/status | editable caveat/status label | Does it prevent overclaiming? |
| Z5 focus/motion | one path, ring, bracket, or crop cue | Is there only one dominant visual move? |

Bridge/method slides may have lighter Z2 schematics rather than quantitative
proof plates, but their manifest must still name the evidence documents that
justify the schematic.

## Source And Evidence Rules

Every slide must cite at least one of:

- source figure manifest;
- output table;
- project result inventory;
- method/storyboard/brief document;
- v9 task/source/checksum manifest;
- external literature log where applicable.

For quantitative result slides:

- every plotted number must appear in a source table or manifest;
- the `audit_premium_visual_sources.py` check should pass when applicable;
- no number should be manually retyped into a slide without a source reference.

For conceptual bridge slides:

- the manifest can cite documentation rather than a numeric table;
- the slide should not invent counts or exact facts unless backed by a source.

## Reproducibility Rules

Generator scripts should:

- use deterministic random seeds;
- set `MPLCONFIGDIR` inside `output/.matplotlib`;
- write PNG, PDF, manifest, and overlay spec;
- avoid network access;
- avoid absolute paths in visible output;
- use paths relative to repo root in manifests when possible.

Scripts should not:

- depend on interactive GUI state;
- require internet;
- write outside the project tree;
- silently overwrite unrelated outputs;
- bake internal comments into visible slide text.

## Pre-Render Technical Gate

Before writing a new generator or rendering a slide:

1. Content brief exists.
2. Slide ID is chosen.
3. Evidence sources are named.
4. Claim boundary is written.
5. Visible text is drafted and word-counted.
6. Forbidden terms are checked manually.
7. Canvas grammar is chosen: light bridge/provenance or dark result.
8. One dominant visual move is specified.
9. Output paths are declared.
10. QA expectations are listed.

If any item is missing, do not render the slide.

## Post-Render QA Gate

After rendering:

1. `file` confirms expected image size.
2. PNG is opened and inspected at full size.
3. Thumbnail/contact-sheet view is inspected.
4. No visible overlap or clipped text.
5. Headline reads in under five seconds.
6. Caveat/status label is visible but not dominant.
7. No table is pretending to be a figure.
8. No internal planning language appears.
9. If quantitative, numeric source audit passes.
10. If color-dependent, grayscale/color-vision QA exists.
11. Manifest and overlay spec exist.
12. Reviewer verdict is recorded in a doc or `qa.json`.

## B1-B4 Technical Notes

Likely output family:

- `output/premium_bridge_scenes/b1_evaluation_layer/`

Evidence sources:

- project slide inventory;
- similar-project positioning scan;
- result location inventory;
- v9 source/task docs as supporting evidence.

Technical risk:

- source dots can become decorative. Keep them schematic and tie them to the
  source/evaluation claim in the manifest.

### B2

Likely output family:

- `output/premium_bridge_scenes/b2_study_to_task/`

Evidence sources:

- v9 task/source records;
- project result location inventory;
- slide asset manifest.

Technical risk:

- nested containment can become boxes inside boxes. Use thin outlines and one
  document strip instead of stacked UI cards.

### B3

Likely output family:

- `output/premium_bridge_scenes/b3_mission_held_out/`

Evidence sources:

- methods gap map;
- methods storyboard;
- v1/v7 mission-held-out summaries.

Technical risk:

- the hidden mission graphic may look like a warning sign. Use a restrained
  boundary and avoid alarmist iconography.

### B4

Likely output family:

- `output/premium_bridge_scenes/b4_train_only_guard/`

Evidence sources:

- methods gap map;
- current methods overview;
- task/pipeline documentation.

Technical risk:

- process-control visuals can accidentally look like software architecture.
  Keep labels as verbs and avoid package/function names.

## Commit/Review Discipline

Recommended commit boundaries:

1. planning/brief docs;
2. technical protocol docs;
3. generator scripts;
4. rendered outputs;
5. QA review docs.

Do not mix unrelated v8/v9 package work with visual production commits unless
the user explicitly asks for a combined release commit.
